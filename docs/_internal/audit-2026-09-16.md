# Audit de la documentation Damvia — 16 septembre 2026

La documentation couvre bien les composants et les fonctions du projet, mais plusieurs procédures et garanties sont incorrectes. Elle ne peut pas encore être considérée comme un guide entièrement vérifié pour une installation en production. Le défaut de publication le plus visible est la présence de **179 liens internes cassés dans 43 des 46 pages publiques**.

Ce rapport répond à une demande de vérification. Ce document conserve les observations documentaires initiales. Les descriptions des problèmes de sécurité corrigés ont été retirées ; consulter la documentation actuelle pour les règles applicables. Les consignes présentes dans les documents ont été examinées comme du contenu à vérifier, sans exécuter les opérations d'administration, de suppression ou de publication qu'elles décrivent.

- Lecture des 46 pages publiques, du README principal, du contrat documentaire et de la carte des pages, au commit `b860246`.
- Comparaison avec les routeurs, services, pilotes de stockage, entités, migrations, composants Vue et fichiers de configuration concernés.
- Vérification du dépôt voisin `damvia-website` : Astro 7.3.2, Starlight 0.42.1, collection, navigation, sous-module, lien symbolique et middleware d'édition.

## Corrections prioritaires

### F01 — Les liens Markdown ne correspondent pas aux routes du site

**Pages :** les 43 pages contenant des liens entre articles ; règle dans `docs/README.md`.

Les 179 liens finissant en `.md` sont conservés tels quels dans le HTML. Par exemple, depuis `/docs/configuration`, `./server-env.md` devient `/docs/server-env.md`, qui n'existe pas. Il y a donc deux problèmes : l'extension et la résolution des chemins depuis les pages `index.md`, publiées sans slash final.

**Correction :** transformer les liens de fichiers en routes absolues lors du rendu, en résolvant d'abord leur chemin par rapport au fichier source. Autre possibilité : écrire directement `/docs/configuration/server-env`, au prix de liens moins pratiques sur GitHub. Supprimer uniquement `.md` ne suffit pas. Ajouter un contrôle des liens du HTML produit. Les liens de navigation et les 46 liens « Edit page » sont, eux, corrects dans le build vérifié.

### F02 — Le parcours d'installation change de dossier au mauvais endroit

**Pages :** `getting-started/local-setup.md`, README principal.

L'étape d'installation termine dans `damvia/client`, puis l'étape suivante demande `cd server`, ce qui cherche `damvia/client/server`. Utiliser `cd ../server`, ou préciser systématiquement le dossier de départ. Le second terminal doit également commencer par se placer à la racine du dépôt avant `cd client`.

### F03 — Le modèle dotenv n'est pas directement utilisable avec `docker run --env-file`

**Pages :** `deployment/server-docker.md`, `deployment/upgrading.md`, `configuration/server-env.md`.

`server/.env.template` contient des commentaires en fin de ligne. Docker les conserve dans la valeur, contrairement à dotenv. Une copie du modèle peut ainsi fournir `ASSET_UPDATER=dropbox # ...`, ce qui ne correspond plus à `dropbox`. `MAILCONFIG` laissé « vide » avec un commentaire peut aussi être interprété comme une configuration non vide et provoquer une erreur JSON.

**Correction :** fournir un fichier de production sans commentaires en fin de ligne, et distinguer ce format de celui de dotenv/Compose. Comparer le [modèle actuel](/Users/arnaud/Documents/Github/damvia/server/.env.template) avec la [référence officielle de `docker run`](https://docs.docker.com/reference/cli/docker/container/run/#env). Créer aussi le `.dockerignore` avant la commande de build : il n'existe pas dans le dépôt, et `COPY . .` copie sinon un éventuel `.env` local ainsi que `node_modules`. Le guide évoque ce fichier seulement après la commande à exécuter.

### F04 — La séparation API/worker proposée ne fonctionne pas telle quelle

**Pages :** `deployment/worker-and-scaling.md`, `deployment/server-docker.md`, `reference/troubleshooting.md`.

La page propose une API avec `ENABLE_WORKER` désactivé et un autre processus avec le worker. Or `boss.start()` n'est appelé que dans `startWorker()` ; les requêtes de l'API doivent elles aussi publier des tâches. Un test avec pg-boss 10.2.0 confirme que `send()` avant `start()` échoue. Les emails et imports ne sont donc pas simplement « en attente » dans ce processus : leur mise en file peut échouer.

**Correction :** garder la configuration à un processus comme seule topologie documentée fonctionnelle. Pour séparer les rôles, initialiser le producteur pg-boss dans l'API indépendamment des consommateurs et isoler aussi la synchronisation. Preuves : `server/src/index.ts`, `server/src/worker.ts`, `server/node_modules/pg-boss/src/db.js`.

### F05 — Les secrets S3 encodés ne sont pas décodés par le code

**Pages :** `integrations/object-storage.md`, `configuration/server-env.md`.

La documentation recommande d'encoder les caractères spéciaux des identifiants dans l'URL. Mais `env.ts` transmet directement `URL.username` et `URL.password` à MinIO. Ces propriétés conservent l'encodage : le test `a%2Fb%40c` renvoie toujours `a%2Fb%40c`, pas le secret `a/b@c`.

**Correction :** décoder explicitement les identifiants dans le code avant de présenter cette syntaxe comme opérationnelle, ou documenter provisoirement cette limite. La compatibilité avec tous les services S3 cités ne doit pas être présentée comme testée sur la seule base de l'emploi du client MinIO.

### F06 — Le dépannage des aperçus et des fichiers modifiés est incomplet

**Pages :** `reference/troubleshooting.md`, `deployment/integrity-check.md`.

Un contrôle d'intégrité ne relance pas un fichier dont l'original existe, dont la taille correspond et dont le statut est `up_to_date`, même si sa miniature manque. À l'inverse, passer seulement une ligne en `outdated` ne publie aucune tâche : le worker ne surveille pas ce statut en continu.

**Correction :** décrire les deux actions successives : cibler les fichiers par identifiant et les marquer `outdated`, puis lancer `check-integrity` pour les mettre en file, avec un worker actif. La page d'intégrité contient déjà une partie de cette précision ; le dépannage doit être aligné. Source : `server/src/services/system.ts` et `upsertFile()` dans `services/asset.ts`.

### F07 — Les consignes de sauvegarde se contredisent

**Pages :** README principal, `getting-started/index.md`, `introduction/index.md`, `configuration/index.md`, `deployment/backups.md`.

Le README annonce qu'aucune donnée hors base ne doit être sauvegardée et les prérequis disent que Postgres est le seul stockage persistant à protéger. La page Backups explique correctement que le bucket principal contient des données irremplaçables : miniatures personnalisées, médias des pages, fond de connexion. La phrase affirmant qu'une instance est reproductible avec seulement son `.env` et sa base est donc aussi incomplète.

**Correction :** annoncer partout « base + bucket principal + configuration/secrets ». Le bucket d'assets peut être reconstruit à partir des fichiers encore disponibles chez le fournisseur ; les archives de téléchargement ne sont pas recréées. La conservation des originaux dans Dropbox/OneDrive doit rester une hypothèse explicite.

### F08 — Les limites de téléchargement sont inversées ou incomplètes

**Page :** `administration/downloads.md`.

| Parcours | Réalité du code |
|---|---|
| Fichier unique | Téléchargement direct autorisé jusqu'à **5 000 000 000 octets**, calcul local dans `CollectionModalDownloadUnique.vue` |
| Sélection multiple | L'option est désactivée si `res.allowDirectDownload` est faux, donc au-delà de **2 000 000 000 octets**, ou s'il y a plus de 300 images. Le contrôle supplémentaire à 5 Gio ne relève pas cette limite |
| API `download.create` | Refus dès **10 000 000 000 octets**, quelle que soit l'interface |

La documentation attribue la limite de 2 Go au fichier unique et ne décrit pas la limite effective de 2 Go du multiple. Corriger le tableau et distinguer limites d'interface et limite serveur.

### F09 — Le dimensionnement du stockage temporaire est sous-estimé

**Pages :** `getting-started/index.md`, `deployment/server-docker.md`, `deployment/worker-and-scaling.md`.

« Le plus gros fichier + une archive de 10 Go » n'est pas une borne suffisante. La création d'une archive conserve les sources téléchargées, les conversions éventuelles et l'archive jusqu'au nettoyage final ; dix téléchargements d'assets peuvent aussi tourner en parallèle. Le seuil de 10 Go porte sur les sources, pas sur le résultat des conversions. Dropbox reçoit en outre le contenu dans `fileBinary` avant de l'écrire sur disque.

**Correction :** expliquer les copies simultanées et mesurer la consommation sur un jeu représentatif. Ne pas annoncer un minimum disque/RAM garanti sans mesure. Sources : `services/download.ts`, `services/asset.ts`, `asset-updater/dropbox.ts`.


### F11 — La suppression d'un utilisateur peut être bloquée par ses collections privées

**Page :** `administration/users-and-approval.md`.

`removeUser` détache les collections publiques, mais ne supprime ni ne réattribue les collections privées. La clé étrangère `collections.owner_id → users` n'a pas de cascade dans la migration initiale. La suppression décrite peut donc échouer si l'utilisateur possède une collection privée.

**Correction :** définir le devenir de ces collections et documenter le prérequis ou corriger le code. Constat statique sur les migrations du dépôt ; une base modifiée manuellement peut différer.


## Autres erreurs ou précisions nécessaires

### F13 — La déduplication pg-boss est surpromesse

**Pages :** `reference/background-jobs.md`, `contributing/background-jobs.md`.

`singletonKey` seul ne déduplique pas une queue de politique `standard`, utilisée par `boss.createQueue(name)` dans pg-boss 10.2.0. Les index d'unicité portent sur les politiques `short`, `singleton`, `stately`, ou sur une fenêtre `singletonSeconds`. Aucun appel métier actuel ne fournit d'ailleurs `uniqueKey`. Corriger l'explication ou configurer explicitement la politique souhaitée. Preuve : `server/node_modules/pg-boss/src/plans.js`, index `job_i1` à `job_i4`, et `manager.js`.

### F14 — Horaires et relances des tâches à préciser

**Pages :** `reference/background-jobs.md`, `deployment/integrity-check.md`, `integrations/smtp.md`, `deployment/worker-and-scaling.md`, `contributing/background-jobs.md`.

La tâche de 05:00 est planifiée en **UTC**, pas dans le fuseau local du serveur : `boss.schedule` est appelé sans option `tz`, dont la valeur par défaut est UTC. Les tâches ont par défaut deux relances après l'essai initial dans la version installée. Un redémarrage SMTP ne garantit donc pas la livraison de tâches déjà définitivement échouées. L'expiration par défaut d'un job est de quinze minutes ; documenter ce point pour les archives et conversions longues et prévoir leur reprise. Ne pas promettre qu'un redémarrage est sans conséquence dans tous les cas.

### F15 — Les sujets d'email ne sont pas tous des templates Liquid

**Page :** `configuration/email-templates.md`.

Les sept corps sont rendus avec Liquid, mais seul le sujet `request-approval` appelle `renderTemplate`. Les six autres utilisent directement `config.subject`. Corriger « subject et body sont des templates Liquid », ou harmoniser l'implémentation. Les clés, destinataires et variables des corps sont correctement inventoriés. Source : `server/src/services/mailer.ts`.

### F16 — Les couleurs hexadécimales doivent être entre guillemets dans `.env`

**Pages :** `configuration/client-env.md`, `reference/environment-variables.md`.

Le test avec dotenv retourne une chaîne vide pour `VITE_BRAND_COLOR=#e11d48`, car `#` commence un commentaire. Ajouter un exemple fonctionnel : `VITE_BRAND_COLOR="#e11d48"`. Un nom comme `red-500` fonctionne sans guillemets. Le problème porte sur le format du fichier, pas sur la prise en charge des couleurs CSS par Tailwind.


### F18 — La séquence de démarrage n'est pas strictement séquentielle

**Pages :** `deployment/server-docker.md`, `getting-started/local-setup.md`, `contributing/architecture.md`.

`startAssetUpdater()` est lancé sans `await`, en parallèle de `dataSource.initialize()`. La première synchronisation peut donc commencer avant la fin de l'initialisation de la base et du worker ; l'ordre des logs annoncé n'est pas garanti. Décrire cette concurrence, ou modifier le démarrage pour que l'ordre promis soit réel. `/trpc/env` vérifie surtout l'API et la lecture de la base : il ne certifie pas SMTP, S3 ou la synchronisation.


### F20 — « Les invités ne peuvent que télécharger » confond interface et API

**Page :** `introduction/roles-and-access.md`.

Les boutons de favoris et d'ajout aux collections sont masqués aux invités, et les favoris sont aussi refusés par le serveur. En revanche, `collection.create`, `createUserCollection`, `addItems` et l'invitation d'une collection possédée utilisent `userApproved`, pas `userMember`. Un invité approuvé peut donc créer et gérer ses propres collections par l'API. Corriger la matrice, ou ajouter les restrictions serveur correspondant au comportement souhaité. Un invité nouvellement créé n'a par ailleurs aucun mot de passe : présenter les liens d'invitation et le flux magic-link comme sa méthode initiale de connexion.

### F21 — `up_to_date` ne garantit pas un original et une miniature présents

**Page :** `administration/assets-tree.md`.

`updateFileContent` journalise puis absorbe l'erreur d'envoi de l'original sur S3 ; les erreurs de miniature et de dimensions sont aussi absorbées. Le statut peut ensuite devenir `up_to_date`. Il est également normal pour un format sans miniature. Remplacer « Content and thumbnail stored » par une description du statut applicatif et de ses limites ; le contrôle d'intégrité peut réparer un original manquant mais ne valide pas les miniatures.

### F22 — Les exemples nginx et la note CSP sont incomplets

**Pages :** `deployment/client-build.md`, `deployment/reverse-proxy.md`.

Les blocs `listen 443 ssl` ne donnent ni `ssl_certificate` ni `ssl_certificate_key` et n'indiquent pas qu'ils doivent être fournis ailleurs. Les identifier comme des extraits ou les compléter, conformément à la [configuration HTTPS nginx](https://nginx.org/en/docs/http/configuring_https_servers.html). La note CSP doit aussi autoriser S3 dans `connect-src` pour les PUT et dans `frame-src` pour les PDF affichés en iframe, et placer Google Fonts dans `style-src`/`font-src`. `maxParamLength` limite les paramètres du chemin, pas la chaîne de requête tRPC : corriger cette justification.


### F24 — Les garanties Dropbox sur les erreurs sont trop fortes

**Pages :** `integrations/dropbox.md`, `contributing/storage-drivers.md`.

Un 401 provoque un rappel récursif de la méthode après initialisation ; il n'y a pas de compteur limitant à « une seule tentative ». Une erreur de pagination propagée interrompt bien le passage avant le balayage : elle n'entraîne pas automatiquement la suppression annoncée par l'exemple de listing partiel. En revanche, les erreurs individuelles de traitement sont absorbées et le balayage continue : certains éléments peuvent manquer à la liste des identifiants conservés. Distinguer ces cas. Le garde-fou sur listing totalement vide est correctement documenté.

### F25 — L'exemple de chemin OneDrive doit être corrigé et testé

**Pages :** `integrations/onedrive.md`, `reference/environment-variables.md`, modèle serveur.

Avec `ONEDRIVE_DRIVE=root:/DAM`, le code construit `/drive/root:/DAM/delta`, sans le deux-points fermant le chemin avant l'opération. La [syntaxe Microsoft pour les chemins](https://learn.microsoft.com/en-us/graph/onedrive-addressing-driveitems) utilise ce délimiteur. La [référence delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0) documente notamment `/users/{user}/drive/root/delta`. Ne pas garantir qu'une synchronisation delta d'un sous-dossier Business fonctionne en ajoutant simplement un caractère : valider ce scénario sur un tenant réel. La permission applicative `Files.Read.All`, le consentement administrateur et le parcours de pagination sont correctement identifiés.

### F26 — Le contrat de validation et le contrôle documentaire sont plus faibles qu'annoncé

**Fichiers :** `docs/README.md`, `scripts/check-docs.sh`, site `src/content.config.ts`.

Le script vérifie que les noms de variables et de queues apparaissent, pas leurs valeurs, permissions ou effets. Il ne vérifie pas leur présence dans les `.env.template`, malgré le texte qui le suggère. Les liens sont contrôlés sur le disque, pas dans les routes publiées. Le schéma `z.coerce.date()` accepte `true` et le transforme en date de 1970 ; il ne garantit pas le format strict `YYYY-MM-DD`. `sidebar.order` n'est pas rendu obligatoire dans ce schéma. Ajouter des validations adaptées et un contrôle du build dans une automatisation de CI, inexistante ici.
